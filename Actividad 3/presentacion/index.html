Arquitectura de Seguridad

La Transición hacia el Modelo Zero Trust en Horizonte

De un esquema artesanal expuesto a ataques a una infraestructura protegida en profundidad.

⚠️ Vulnerabilidades Previas

TELNET transmitiendo contraseñas en claro, acceso directo a root, claves de host clonadas y servicios internos expuestos a redes no confiables.

🛡️ Pilares de la Solución

  • KEX Híbrido Post-Cuántico
  • Confinamiento de roles con Chroot
  • Defensa perimetral con Fail2ban/nftables

Criterio 1: 3 Puntos

Identidad Criptográfica y KEX Híbrido Post-Cuántico

Erradicación de claves clonadas y mitigación de ataques "Harvest Now, Decrypt Later".

🔑 El Peligro de Claves de Host Clonadas

En imágenes de contenedores, la clave original contenía root@buildkitsandbox. Si múltiples servidores comparten esa clave privada, cualquiera puede perpetrar un ataque de intermediario (MitM).

rm -f /etc/ssh/ssh_host_* ssh-keygen -A # Nueva huella propia: root@srv-horizonte
⚛️ KEX Híbrido Post-Cuántico en OpenSSH 9.6
debug1: kex: algorithm: sntrup761x25519-sha512@openssh.com debug1: kex: host key algorithm: ssh-ed25519 debug1: kex: server->client cipher: chacha20-poly1305

Combina X25519 con Streamlined NTRU Prime 761 (retículos), protegiendo contra futuros ordenadores cuánticos.

Criterio 2: 3 Puntos

Autenticación por Claves Asimétricas Ed25519

Eliminación total de contraseñas y control estricto de permisos POSIX.

🛡️ Separación de Claves y Permisos (StrictModes)
  • Clave Privada (`id_ed25519`): Permanece únicamente en el cliente (permisos 600).
  • Clave Pública (`id_ed25519.pub`): Autorizada en `authorized_keys` del servidor (permisos 600).
  • Directorio `~/.ssh`: Permisos estrictos 700. OpenSSH rechaza el inicio si otros tienen escritura.
⚙️ Configuración del Cliente (`~/.ssh/config`)
Host horizonte HostName 127.0.0.1 User estudiante IdentityFile ~/.ssh/id_ed25519 IdentitiesOnly yes # Conexión instantánea sin contraseña interactiva: $ ssh horizonte whoami estudiante
Criterio 2: 3 Puntos

Endurecimiento Modular (`10-horizonte.conf`)

Regla de oro: "Primera aparición gana" en `/etc/ssh/sshd_config.d/`.

📜 Directivas de Endurecimiento Institucional
PermitRootLogin no PasswordAuthentication no AuthenticationMethods publickey AllowGroups sshadmins sftp-web MaxAuthTries 3 LogLevel VERBOSE Banner /etc/issue.net X11Forwarding no
🔍 Impacto de Seguridad
  • `PermitRootLogin no`: Bloquea al usuario más codiciado por atacantes.
  • `AuthenticationMethods publickey`: Cero contraseñas.
  • `AllowGroups`: Control de acceso por roles (RBAC).
  • `LogLevel VERBOSE`: Registra huellas digitales SHA256 de las claves para auditoría forense.
Criterio 2: 3 Puntos

Confinamiento Seguro: SFTP Enjaulado para Comunicación

La regla de propiedad estricta de OpenSSH y aislamiento de terminal.

🔒 Regla de Oro del ChrootDirectory

Si `/srv/horizonte` no pertenece a root:root o tiene permisos de escritura de grupo, OpenSSH aborta con: fatal: bad ownership or modes for chroot directory

chown root:root /srv/horizonte chmod 755 /srv/horizonte # Subida compartida en /www: chmod 2775 /srv/horizonte/www chown root:webadmin /srv/horizonte/www
🚫 Pruebas con Usuario `comunicacion`
sftp> pwd -> Remote working directory: /www sftp> cd /etc -> stat remote: No such file or directory # Intento de sesión SSH interactiva: PTY allocation request failed on channel 0 This service allows sftp connections only.
Criterio 3: 4 Puntos

Defensa Activa con Fail2ban sobre Nftables

Mitigación en tiempo real de ataques de fuerza bruta en Ubuntu 24.04 LTS.

⚡ Integración con Systemd Journal
# /etc/fail2ban/jail.d/horizonte-ssh.local [sshd] enabled = true backend = systemd journalmatch = _SYSTEMD_UNIT=ssh.service + _COMM=sshd maxretry = 4 findtime = 10m bantime = 1h bantime.increment = true
🧱 Filtrado en Nftables a Nivel de Kernel

Fail2ban inyecta la IP atacante en la tabla inet f2b-table addr-set-sshd. El kernel descarta los paquetes antes de que alcancen el demonio SSH.

$ fail2ban-client status sshd `- Actions: Currently banned: 0, Total: 2 $ fail2ban-client set sshd unbanip <IP>
Criterio 2 y 3

Túneles SSH: Acceso a Microservicios Internos

Consumo seguro de APIs enlazadas en bucle local (`127.0.0.1:8081`).

🌐 Túnel Local (-L 9081:127.0.0.1:8081)
ssh -N -L 9081:127.0.0.1:8081 horizonte # Consulta en cliente local: curl http://127.0.0.1:9081/eco { "metodo": "GET", "ruta": "/eco", "cliente": "127.0.0.1", "Host": "127.0.0.1:9081" }
🎯 Ventajas de Seguridad
  • Cero Exposición: El microservicio no escucha en 0.0.0.0. Es invisible en Internet.
  • Cifrado Gratuito: El tráfico viaja protegido por ChaCha20-Poly1305.
  • Modalidades:
    • `-L`: Túnel local hacia un servicio fijo.
    • `-D`: Proxy dinámico SOCKS5 en el puerto 1080.
    • `-J`: Salto a través de bastiones intermedios.
Criterio 3: 4 Puntos

Política Institucional de Acceso Remoto (U.E. Horizonte)

Marco normativo obligatorio aprobado bajo código POL-SEC-03-2026.

📋 Normativa Criptográfica y Roles
  • Prohibición total: TELNET y contraseñas interactivas prohibidas.
  • Custodia de claves: Claves privadas Ed25519 personales, protegidas con passphrase. Rotación obligatoria cada 6 meses.
  • Grupos autorizados: Solo `sshadmins` (shell/sudo) y `sftp-web` (SFTP enjaulado).
🚨 Monitoreo y Defensa Activa
  • Fail2ban activo: Bloqueo automático a los 4 intentos fallidos en 10 min.
  • Baneo exponencial: Duplicación del tiempo de castigo ante reincidencias.
  • Auditoría Forense: Registro obligatorio de huellas digitales SHA256 en Journald.

Conclusiones Finales

Conclusiones y Preguntas de Defensa Oral

Preparados para responder con solvencia técnica ante el M.Sc. Ing. Jimmy Requena.

1. Oscuridad vs Claves

Cambiar de puerto es inútil frente a nmap -sV. Exigir Ed25519 y AllowGroups vuelve matemáticamente imposible la fuerza bruta.

2. Host Cambiado

Nunca borrar con ssh-keygen -R a ciegas. Siempre verificar la huella SHA256 fuera de banda para descartar un ataque MitM.

3. Chroot a Root

La raíz debe ser de root:root (755) para evitar que el usuario manipule librerías y escape del confinamiento.
