2. Preparación del entorno 
2.1. Reglas de seguridad 
• Realiza pruebas únicamente contra las máquinas y contenedores del curso, nunca contra servidores ajenos.  
• No pegues claves privadas ni credenciales reales en la IA, capturas o repositorios. La clave privada permanece en el

Windows con la terminal Linux.

3. Laboratorio 10 — TELNET vs SSH 
Objetivo: demostrar que TELNET expone el contenido de la sesión y SSH lo cifra; regenerar claves de host clonadas; crear y 
autorizar una clave ed25519; conectarse mediante el alias horizonte y publicar comunicado.html por scp.  
3.1. Auditoría inicial 
sudo -i 
cd ~/lab10 
ssh -V 
ss -tlnp | grep -E ':22|:23'  
 
Registra la versión de OpenSSH y qué puertos están escuchando. Que TELNET esté inicialmente desactivado en Ubuntu 
24.04 es normal. 
3.2. Capturas controladas 
bash telnet_laboratorio.sh activar 
bash capturar.sh telnet 
bash capturar.sh ssh 
 
Los scripts crean datos temporales de prueba y guardan resultados en resultados/. Usa solo las credenciales de 
demostración de la guía y nunca reutilices contraseñas reales. 
Aspecto TELNET (23) SSH (22) 
Usuario y contraseña Pueden leerse en claro en la captura. No deben aparecer como texto de la sesión. 
Contenido escrito Puede verse en claro. Va cifrado; puede verse el banner de versión. 
Conclusión No usar para administración en redes no 
confiables. 
Usar SSH con verificación de identidad y 
claves. 
 
3.3. Inspeccionar PCAP en Wireshark 
• Abre resultados/telnet.pcap en Wireshark. 
• Selecciona un paquete de la sesión y usa Analizar → Seguir → Flujo TCP. 
• Identifica usuario, contraseña y texto de prueba visibles en claro; captura la pantalla sin información personal ajena.  
• Abre resultados/ssh.pcap y verifica que no se lea la contraseña ni el contenido de la sesión en claro. 
• Completa la tabla comparativa en HOJA_TRABAJO.md y guarda las capturas en la carpeta de evidencias.

3.4. Regenerar identidad del servidor 
Las claves de host copiadas dentro de una imagen pueden hacer que muchos contenedores o VM compartan la misma 
identidad. Completa el TODO 1 de preparar_ssh.sh y verifica la nueva huella. 
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub 
bash preparar_ssh.sh <usuario_admin> 
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub 
 
Aviso de host cambiado 
REMOTE HOST IDENTIFICATION HAS CHANGED puede deberse a una regeneración prevista o a un ataque de 
intermediario. Comprueba la huella por un canal confiable antes de actualizar known_hosts; no borres la advertencia a 
ciegas. 
 
3.5. Clave ed25519, permisos y alias 
ssh-keygen -t ed25519 -a 64 -C "admin-horizonte-2026" 
bash preparar_ssh.sh <usuario_admin> 
stat -c '%a %n' /home/<usuario_admin>/.ssh /home/<usuario_admin>/.ssh/authorized_keys 
ssh horizonte whoami 
 
• id_ed25519 es la clave privada: no sale del cliente. 
• id_ed25519.pub es la clave pública: se autoriza en authorized_keys del usuario. 
• Permisos esperados: ~/.ssh = 700 y authorized_keys = 600, con propietario correcto. 
• El alias Host horizonte debe definir HostName, User, IdentityFile e IdentitiesOnly yes. 
3.6. Publicar con scp y cerrar Lab 10 
scp comunicado.html horizonte:/srv/horizonte/www/ 
ssh horizonte "ls -l /srv/horizonte/www/comunicado.html" 
bash telnet_laboratorio.sh desactivar 
ss -tln | grep ':23 ' || echo "TELNET desactivado: puerto 23 cerrado" 
bash verificar_lab10.sh <usuario_admin> 
 
Criterio de cierre Lab 10 
El verificador debe informar 11 de 11; TELNET queda desactivado; comunicado.html está publicado con propietario y 
grupo correctos.

4.1. Preflight y dos sesiones 
sudo -i 
cd ~/lab11 
ssh horizonte whoami 
sshd -T | grep -E 'permitrootlogin|passwordauthentication|maxauthtries|loglevel'  
 
No continúes si el acceso por clave del Lab 10 no funciona. Mantén dos sesiones abiertas durante los cambios.  
4.2. Endurecer sshd 
# /etc/ssh/sshd_config.d/10-horizonte.conf 
PermitRootLogin no 
PasswordAuthentication no 
AuthenticationMethods publickey 
AllowGroups sshadmins sftp-web 
MaxAuthTries 3 
LoginGraceTime 20 
KexAlgorithms sntrup761x25519-sha512@openssh.com,curve25519-sha256 
LogLevel VERBOSE 
Banner /etc/issue.net 
 
sshd -t 
# Reinicia solo si sshd -t no informa errores: 
systemctl restart ssh 
sshd -T | grep -E 'permitrootlogin|passwordauthentication|maxauthtries|loglevel' 
ssh horizonte whoami 
 
Evita bloquearte 
Si sshd -t muestra un error, corrige el archivo antes de reiniciar. Conserva la sesión administrativa abierta y confirma que 
ssh horizonte continúa funcionando. 
 
4.3. SFTP enjaulado 
Match Group sftp-web 
    ChrootDirectory /srv/horizonte 
    ForceCommand internal-sftp -d /www -u 0002 
    AllowTcpForwarding no 
    PermitTTY no 
 
Ruta Propietario/permisos Función 
/srv root:root · 755 Ruta base. 
/srv/horizonte root:root · 755 Raíz del chroot; no debe ser escribible por la 
cuenta enjaulada. 
/srv/horizonte/www root:webadmin · 2775 Carpeta de publicación con grupo 
compartido. 
 
sftp comunicacion@srv-horizonte 
# Dentro de SFTP: 
pwd 
cd /etc 
exit 
ssh comunicacion@srv-horizonte 
 
Resultado esperado: pwd muestra /www; cd /etc falla porque la ruta queda fuera de la jaula; SSH interactivo informa que 
solo se permiten conexiones SFTP.

4.4. Fail2ban: configuración y diagnóstico 
La guía oficial de Lab 11 propone la configuración siguiente. Completa los TODO en fail2ban/horizonte -ssh.local y ejecuta 
endurecer_ssh.sh. 
Configuración objetivo de la guía oficial Lab 11 
[sshd] 
enabled = true 
mode = aggressive 
journalmatch = _SYSTEMD_UNIT=ssh.service + _COMM=sshd 
maxretry = 4 
findtime = 10m 
bantime = 1h 
bantime.increment = true 
 
fail2ban-client status sshd 
fail2ban-client get sshd ignoreip 
fail2ban-client get sshd journalmatch 
fail2ban-client get sshd bantime 
 
No mezclar configuraciones 
En la guía oficial se documentan maxretry=4 y bantime=1h. En la demostración Docker verificada el 21/10/2026 se 
observó maxRetry=5, findtime=600 y banTime=600. Para repetir exactamente esa demostración usa los valores reales 
del contenedor; para entregar el laboratorio sigue los archivos y el verificador oficiales. 
 
4.5. Prueba controlada de bloqueo en Docker 
La demostración verificada utilizó tw1-seguridad-servidor (172.22.0.2) y tw1-cliente-fail2ban (172.22.0.3). Las IP pueden 
cambiar si se recrea la red; confírmalas antes de repetir. 
docker ps --filter "name=tw1" --format "table {{.Names}}\t{{.Status}}" 
docker exec tw1-seguridad-servidor fail2ban-client status sshd 
docker exec tw1-seguridad-servidor bash -c "tail -n 30 /var/log/fail2ban.log" 
docker exec tw1-seguridad-servidor nft list set inet f2b-table addr-set-sshd 
 
# Un intento controlado desde el contenedor cliente: 
docker exec tw1-cliente-fail2ban ssh -i /tmp/clave_prueba_fail2ban -o IdentitiesOnly=yes -o BatchMode=yes -o 
ConnectTimeout=5 usuario_inexistente_tw1@172.22.0.2 exit 
 
Repite únicamente el número de intentos que corresponda a maxretry en el entorno de práctica. Permission denied por sí 
solo no prueba el bloqueo. La evidencia válida combina el evento Ban, el estado del jail y la IP en nftables.  
docker exec tw1-seguridad-servidor fail2ban-client status sshd 
docker exec tw1-seguridad-servidor nft list set inet f2b-table addr-set-sshd 
docker exec tw1-seguridad-servidor bash -c "grep -E 'Found|Ban |Unban|ERROR' /var/log/fail2ban.log | tail -n 20" 
 
4.6. Expiración automática 
Anota la hora UTC de Ban y espera el bantime completo. No uses unbanip durante esta evidencia: el objetivo es probar la 
expiración automática. 
docker exec tw1-seguridad-servidor date -u '+%Y-%m-%d %H:%M:%S UTC' 
docker exec tw1-seguridad-servidor fail2ban-client status sshd 
docker exec tw1-seguridad-servidor bash -c "grep -E 'Ban 172\\.22\\.0\\.3|Unban 172\\.22\\.0\\.3' /var/log/fail2ban.log 
| tail -n 5" 
docker exec tw1-seguridad-servidor nft list set inet f2b-table addr-set-sshd
